# CU transport: decisions and limits

Baseline is commit 221c870 (branch feat/reliable-harness-cu-20261105); candidate is the working tree. The public adapter is independently written. It loads the user-configured local bridge; no private source, native binary, account path, or credential is included here.

- NDJSON stdio limits requests to 256 KiB and inline responses to 2 MiB. Larger responses are retained by SHA-256 under the private transport state directory, copied with hash verification into the execution context's artifact directory, and represented by a bounded summary and artifact block. This does not yet use the runtime ArtifactStore API or its retention/GC policy.
- The default machine state is one per-user directory under the user's local state directory, independent of the transport artifact directory. Its lifetime lock and ledger cover all sidecars using that default. A deliberate GCODE_CU_MACHINE_DIR override must be the same for every invocation; this is application-level mutual exclusion, not an OS sandbox against deliberately different configurations or another desktop-control application. A crash can leave a lock containing process identity; verify the previous process and its children have exited before manually removing it.
- Writes require action IDs, a durable ledger entry before dispatch, matching run/session ownership, and caller authorization. Duplicate IDs must have the same owner, method and parameters; they return the existing response or unknown, never dispatch again. Unknown, incomplete receipt, timeout or action exception stops new writes across runs and sidecar restarts. A restart after an uncleanly ended owner with prior actions stops writes because original bridge scope and text-dedup state live in memory. An explicit clean shutdown can instead close an owner when all outcomes are known; the next owner must obtain a fresh complete task-window binding, and closed owners cannot make new writes. Read-only observations do not clear the fence. Request correlation does not prove exactly-once OS delivery.
- The original native stdout and CLI status are preserved, and typed disposition is mapped only when command/action and explicit disposition agree. The separate keyboard bridge's typed receipt is classified only on its expected command, type, event count and original success. Missing/mismatched receipt remains unknown. `delivered_unverified` means possible delivery, never completion. Native failure may involve focus preparation; read the full receipt and do not interpret `not_delivered` as proof that focus could not change. No retry is added.
- A child run never receives write access, even when it asks. Tools are opt-in. Use provider-advertised schemas; preserve complete raw response and content. Native scope, refs, focus, keyboard and unknown fences remain the original bridge's responsibility.
- The user-local Pi provider uses a small host registration adapter and configured installed extension, SDK, TypeScript loader and original native binary. GCODE_PI_EXTENSION and GCODE_PI_SDK_PACKAGE are explicit absolute paths; PI_AGENT_DESKTOP_BINARY, PI_AGENT_DESKTOP_APP and PI_AGENT_DESKTOP_ALLOWED_APPS configure the original bridge. PI_CU_WINDOW_KEYBOARD is optional. No GUI call is made by hello. Original private source and schemas are not published in these records.
- Hello identifies protocol, platform, process PID/start/nonce, adapter, extension, native/optional keyboard and SDK package hashes, plus schema hash. If GCODE_PI_MANIFEST is configured it verifies each frozen manifest file and dependency and reports manifest and aggregate hashes; mismatches fail closed. Without it, manifest_verified is false. The manifest does not cover all Node SDK transitive code, signatures, or every system dependency; this is not yet a complete release attestation.
- `cancel` during an active call reports cancellation unconfirmed and potentially unknown; it does not claim the provider was interrupted. Cancelling the Python call closes the channel and the sidecar records in-flight write uncertainty on EOF. A read may be used for inspection; never replay an uncertain action. A stuck underlying action can require stopping the process after determining its state.

## Verification and remaining work

Synthetic subprocess and tool tests use an expressly synthetic provider; see cu-test-results.xml/log and cu-test-evidence.json. They are not evidence of native guard fidelity or task success. The integrator observed native hello and a read-only Finder window inventory through DesktopTool.invoke; the sanitized result is cu-native-read-summary.json. Full raw schema and window evidence remains private. Reversible actions, comparison with the frozen original, end-to-end model requests, packaging, final release manifest, ArtifactStore retention, cancellation recovery and the paired task set remain necessary before full acceptance.

Rollback: disable opt-in desktop tools, stop sidecar after handling pending actions, and retain machine ledger and artifacts. Do not replace or edit the installed Pi release. Never clear unknown by switching a directory or deleting its state.

## Preparation-only launch correction

The first real Calculator launch was dispatched once and returned a native successful launch receipt, but the earlier adapter mapped it to `delivery_unknown` because the native launch command does not emit a payload disposition. The resulting stopped ledger and original unknown response were preserved. A later, independently dispatched read-only window inventory matched the launch PID, process instance and window. The inventory's accessibility flag was not sufficient to authorize an action; a new complete observation remains required.

`reconcile-preparation.mjs` is an explicit local operator procedure for this narrow case, with the sidecar stopped and the machine lock acquired. It requires the exact original action fingerprint and hashes of the original and fresh evidence files; verifies that the only ledger action is the unknown, explicitly background `launch` and no payload action exists; checks original native receipt, original bridge stop flag, successful complete same-window AX, matching frozen bridge/native/manifest hashes, and a recent independent process's successful native window inventory with the same app, window, PID and process instance. On success the ledger retains the original unknown response and records an audit entry and `preparation_reconciled` state; the inferred launch delivery is `delivered_unverified`, never verified business completion. Any mismatch, old evidence, extra action, stopped bridge, incomplete AX, focus or business payload refuses reconciliation. On restart only this one explicitly reconciled preparation is eligible to resume; a subsequent unknown input stops writes and cannot use this procedure to clear the fence.

The procedure does not re-dispatch launch and does not accept a general action, a typed input, click, keyboard payload, focus request or a missing receipt. It relies on the explicitly selected local evidence files and owner-controlled machine directory; it is not a tamper-proof attestation against the machine owner. No automatic reconciliation is performed. The operator must first verify the original process has exited and use the same machine directory; do not switch directories to bypass state. Synthetic negative tests and a dry run against a copy of the real ledger are evidence for the logic only, not evidence that the real ledger was changed.

The operator subsequently ran the earlier reviewed CLI once on the real ledger, before the additional explicit raw-receipt-hash CLI argument was added. That operation checked the original evidence-file hash and exact original ledger response, and recorded the canonical response hash; it did not separately request the raw-block hash. A later read-only audit independently recomputed the raw-block SHA-256 and confirmed the recorded evidence and canonical response hashes; see `cu-preparation-audit-summary.json`. The original unknown response remains in the ledger, and no second reconciliation was run. The current CLI requires the raw-block hash for future qualifying cases. A later fresh full observation and any further action require separate evidence.


## Clean execution-scope closure

Explicit shutdown by the current run/session closes its desktop lease only when there is no active call, the ledger is not stopped, and every action has a known receipt or the narrowly audited preparation reconciliation. A durable closure stores the closed owner and hash of all retained action receipts, then releases the owner. Duplicate old action IDs still return their original receipt; they never dispatch again. A closed owner cannot start another action. A new owner must first obtain a complete current task-window AX observation; a fresh bridge and the original scope/ref protections remain authoritative. Closing a lease does not verify a UI effect or establish task completion.

EOF, crash, unresolved dispatch, unknown delivery, stopped bridge, mismatched owner, missing or tampered receipt never qualifies as a clean close. On restart without a valid matching closure the ledger stops new writes. A later unknown action cannot be cleared by an earlier clean-close record.

For a previous-version sidecar that is known to have exited cleanly, `close-known-run.mjs` is an explicit offline operator procedure: hold the same machine lock, verify the prior process is absent, match the exact owner and all-known ledger, and check hashes of a final complete task-window observation and a separately recorded exit attestation. The attestation records the process PID/nonce and exit code observed by the operator; after the process has exited the CLI cannot independently reconstruct its historical exit code. It is therefore evidence to inspect, not tamper-proof proof. The procedure retains every existing receipt and makes an auditable closure; no unknown payload can pass. Test evidence includes a dry run against a temporary copy of the native ledger, not a modification of the original.
